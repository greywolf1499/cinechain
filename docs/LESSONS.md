# CineChain Developer Lessons & Gotchas
*This is an append-only log of architectural quirks, resolved bugs, and strict constraints to prevent repeating mistakes.*
- **Constraint:** Zero background daemons. All background tasks must use FastAPI `BackgroundTasks`.
- **Constraint:** Do not scrape Letterboxd for heavy metadata (overviews, posters). Only scrape for TMDB IDs, then use the TMDB API.
- **Stack:** React 19, Tailwind v4, Vite 7, Python 3.12. Do not use legacy hooks or outdated syntax.

## Phase 2c: Rabbit Hole Survival Mechanics
- **Bounty rewards:** Challenge engines now own the reward policy through `BaseChallengeEngine.award_bounty`; Rabbit Hole converts the wildcard reward to one life (capped at `max_lives`). Store a server-owned per-step reward marker so undo reverses only a life that was actually awarded.
- **Tier re-rolls:** The single-depth `tier_override` and `lives_remaining` values are server-owned run state. On step deletion, `sync_run_state` clears the override only after that depth's next film is present.
- **Tier 5 ratings:** TMDB fallback ratings are unverified until `vote_count >= 10`; a cached IMDb rating remains authoritative regardless of TMDB vote count. This affects other uses of the shared `rating_of` helper too.
- **Migration validation:** For SQLite migration checks, create the scratch `CONFIG_DIR` before `uv run alembic upgrade head`; Alembic's settings-derived database URL does not create missing parent directories.

## Phase 17a: Backend Bug Squashing
- **Watchlist 404:** `letterboxd.scrape_letterboxd_watchlist` converts a page-1 `curl_requests.exceptions.HTTPError` 404 into `WatchlistNotFound`. SSE routes in `routes_curated.py` now emit structured error bodies (`{code, message, status?, username?}`) via `_error_payload`; `message` is kept for legacy consumers. Codes: `watchlist_not_found` (404), `cloudflare_block` (503), `scrape_failed`, `persist_failed`. Quirk: SSE responses are already HTTP 200 once streaming starts, so the frontend must branch on the `error` event's `code`, not the HTTP status.
- **Metadata:** `overview` was already stored; `tagline` is new (`cached_movies.tagline`, migration `e5f6a7b8c9d0`, exposed on `MovieDetail`). `NULL` = not fetched / cached before taglines existed, `""` = TMDB has none; `GET /movies/{id}` JIT-refreshes rows with a NULL overview or tagline once.
- **Bridge solver:** `TMDBClient` raises `TMDBRateLimitError` (with `retry_after`) after its own retries and `TMDBNotFoundError` on 404. `pathfinder._fetch_with_backoff` pauses via `asyncio.sleep` (escalating, <=30s, honors Retry-After, capped at remaining time) and retries; a 404 node is skipped. The streamed solve ends only on a path, `max_depth`, or `bridge_max_duration_seconds` (deadline now also enforced mid-round, emitting `timeout`). `call_budget` is a hard cap only when passed explicitly (fast `/engine/bridge`, now also capped at 15s); `settings.pathfinder_call_budget` is no longer enforced. Progress events carry `rate_limit_pauses`. All of this stays inside the existing request/SSE lifecycle (no daemons).
- **Files changed:** `services/letterboxd.py`, `api/routes_curated.py`, `services/tmdb.py`, `services/cache_repo.py`, `models/cache.py`, `schemas/movies.py`, `api/routes_movies.py`, `services/pathfinder.py`, `api/routes_engine.py`, `config.py`, migration `e5f6a7b8c9d0`, plus tests in `test_curated_api.py`, `test_pathfinder.py`, `test_tmdb_client.py`.
- **Frontend follow-up (17b):** show `tagline` on cards, branch on SSE `error.code` (`watchlist_not_found`), and surface `rate_limit_pauses` / `timeout` in the Bridge UI.

## Phase 17c: Curator Overhaul & Image Proxy
- **Image proxy (zero-daemon):** `GET /api/images/proxy?url=` (`api/routes_images.py` + `services/image_cache.py`) fetches Letterboxd images JIT with the shared `httpx` client, caches them in `config_dir/cache_images` (`<sha256>.img` + `.json` meta) and returns a `FileResponse`. It honors `Cache-Control`/`Expires` (TTL clamped to 1h-30d, so `no-cache` images are cached briefly then revalidated), revalidates with `ETag`/`Last-Modified` (304 keeps the file), serves a stale copy if the CDN is down, and prunes the cache to 256MB opportunistically after writes (no background worker). **SSRF guard:** https only, no credentials/port, host must be `*.ltrbxd.com`/`*.letterboxd.com`, every redirect hop is re-validated, raster `image/*` only (no SVG), 5MB cap, 4 concurrent upstream fetches. Requires login (img tags send the session cookie). Frontend rule: never put a Letterboxd URL in an `<img>`; use `lib/images.ts#proxiedImageUrl`.
- **Curator modal removed:** `CuratorBrowser.tsx` (and its in-dialog nav stack/pinning) is gone. New routes: `/lists` (all lists), `/curators` (directory), `/curators/:username` (profile). Shared pieces: `ListBrowser` (search/sort/filter/server pagination), `CuratedListCard` (full title, description with Read more, no truncation), `Pagination`, `Breadcrumbs` (Lists > Curators > Name), `CuratorAvatar`, `ListCover`. Settings > Curated Canons keeps preset sync, custom import and watchlist sync, plus links to the new pages; "Discover HQ Accounts" moved to `/curators`. The localStorage `cinechain.pinnedCurators` key is now unused.
- **Server-side browsing:** `GET /curated/lists/browse` (q, sort=name|film_count|popularity|synced, state, account, page) and `GET /curated/accounts/browse` (q, sort, kind, page). Presets are materialized as real rows on browse (`_ensure_preset_rows`) so everything sorts/paginates in SQL. "Popularity" = distinct films of the list already **watched** in any run (`watched_count`), because Letterboxd likes are not scraped.
- **Unified customization:** `curated_lists` gained `slug` (unique), `badge_emoji`, `image_url`, `image_filename`, `image_updated_at` (migration `f6a7b8c9d0e1`, which also backfills slugs and links existing lists to known curator accounts). `PATCH /curated/lists/{id|preset_key|slug}` edits slug (409 on clash), emoji, prefix, color and logo (a Letterboxd image URL, proxy-wrapped URLs are unwrapped, or `clear_image`); `PUT /curated/lists/{id}/image` takes a raw-body PNG/JPEG/GIF/WebP up to 2MB (type sniffed from magic bytes, stored in `config_dir/list_images`), `GET` serves it. Emoji flows to movie badges via `BadgeOut.badge_emoji` -> `CanonBadge`. Custom/preset/discovered lists whose URL is `letterboxd.com/<user>/list/...` are auto-linked to the matching tracked curator account (`_link_to_account`), so they show on that curator's profile.
- **Bug found:** `func.sum(<Boolean column>)` is coerced back to a bool by SQLAlchemy (2 -> True -> 1), so every curator showed at most "1 enabled". Counting now uses `SUM(CASE ...)`. Never SUM a Boolean column directly.
- **Testing quirk:** `GET /curated/accounts/{u}/lists` triggers a real Letterboxd scrape for admins when the account isn't discovered yet - always monkeypatch `letterboxd.discover_user_lists` in tests (an unmocked call took 70s).

## Phase 18a: Multi-Tenant Auth & Zero-Daemon Task Runner
- **Auth (JWT in an HTTP-Only cookie):** `services/security.py` now issues HS256 JWTs (`sub`, `iat`, `exp`, `jti`) via PyJWT, replacing the itsdangerous token (dependency removed, PyJWT added). The `alg` is pinned on decode (no `alg=none`), and `sub/exp/iat` are required. The cookie is `HttpOnly; SameSite=Lax` (`Secure` when `COOKIE_SECURE=true`), so JS can't read it. `/api/auth/{login,logout,me}` already existed; `/me` now renews a session older than 7 days (sliding 30-day expiry), and login runs a dummy bcrypt check for unknown usernames. **Sessions are stateless**: every device holds its own JWT, so Partner A and B (or one person's phone + tablet) are logged in simultaneously and logging out only clears that device's cookie. No server-side session table, so there is no "log out everywhere" lever. The only revocation is rotating `secret.key`. The `User` model already had `password_hash` (bcrypt, 12 rounds; argon2 stays out for RAM reasons), so no schema change. **One-time effect:** cookies issued by the old signer are rejected, so everyone logs in once after upgrading.
- **Task runner:** `models/system.py#SystemTask` (+ migration `a7b8c9d0e1f2`): `id, name, status[pending|running|completed|failed], progress_data(JSON), error, created_at, updated_at` plus `user_id` (visibility) and `dedupe_key`. `services/task_runner.py#submit_task(background_tasks, session, name, work, ...)` inserts the row, schedules `work(ctx)` on the request's own `BackgroundTasks` (a *sync* callable, so Starlette runs it in a worker thread and blocking scrapers never stall the event loop) and returns the task at once (HTTP 202). `TaskContext.progress()` is thread-safe and throttled to one SQLite write per 0.5s; `progress_data` = `{label, progress, result, error}`. Failures are caught and stored (`error` + `progress_data.error` with a machine `code`), never raised into the worker.
- **Zero-daemon guarantees:** no broker/scheduler. At most 2 tasks run concurrently (`_slots` semaphore; extras stay `pending`), so scrapes can't starve the request thread pool. A duplicate `dedupe_key` while one is active returns the existing task. Finished tasks are pruned after 7 days on the next submit. **Restart caveat:** jobs live in the API process, so on startup `fail_interrupted_tasks` marks leftover pending/running rows `failed` ("Interrupted by a server restart"); scrapers checkpoint, so re-running resumes.
- **Task API (`api/routes_tasks.py`):** `GET /api/tasks` (`?active=`, `?limit=`), `GET /api/tasks/{id}`, and SSE `GET /api/tasks/stream` (a `task` event whenever a task's `updated_at` changes, full snapshot first, 15s keep-alive, `?once=true` closes after the snapshot). The stream re-reads SQLite every second inside the request, so it needs no broadcaster. Admins see all tasks; others see only their own (404 for someone else's). Timestamps are returned as UTC with a `Z` suffix (SQLite returns naive datetimes).
- **Migrated operations:** `POST /api/curated/watchlist/sync` and `POST /api/curated/sync/{list_id}` now return `202 + SystemTask` (**breaking change:** they no longer stream SSE). Errors keep their structured codes under `progress_data.error` (`watchlist_not_found`, `cloudflare_block`, ...). Frontend: new `lib/tasks.ts` (`runTask`/`waitForTask` polling, `describeProgress`) used by `CuratedCanonsCard` (watchlist button shows "Syncing... 120/400 films", 404 warning) and `CuratedListCard`. `discover_hq` still uses the old SSE `run_sync_scrape`; it is the next candidate to migrate.
- **Gotchas:** (1) the worker must not reuse the request's DB session (closed after the response); jobs open their own via `ctx.session()` on the engine taken from `session.get_bind()`, which also keeps tests on their isolated DB. (2) TestClient runs BackgroundTasks to completion before returning, so tests can GET the finished task straight after the POST (`_run_task` helper in `test_curated_api.py`). (3) The task row stays the single source of truth; if you add a long job, put its result in `progress_data.result`, never in a side channel.
- **Files:** backend `services/security.py`, `api/routes_auth.py`, `models/system.py`, `models/__init__.py`, `services/task_runner.py`, `api/routes_tasks.py`, `api/routes_curated.py`, `main.py`, migration `a7b8c9d0e1f2`, `pyproject.toml`/`uv.lock`, tests `test_task_runner.py`, `test_tasks_api.py`, `test_auth_api.py`, `test_curated_api.py`; frontend `lib/tasks.ts`, `components/CuratedCanonsCard.tsx`, `components/CuratedListCard.tsx`.

## Phase 19a: History Ingestion & Passport Aggregation (Backend)
- **Endpoints:** `POST /api/passport/import/csv` (multipart field `file`), `POST /api/passport/import/rss` (`{"letterboxd_username"}`), `GET /api/passport/me`, plus `POST /api/passport/backfill-directors`. Both imports return `202 + SystemTask` immediately (task names `diary_import_csv` / `diary_import_rss`; one active import per user via `dedupe_key`). Result: `{run_id, total_rows, imported, skipped_duplicates, unresolved_count, unresolved[<=50 {title, year, reason}], rate_limit_pauses}`; unresolved reasons: `no_tmdb_match`, `not_found_on_tmdb`, `invalid_date`, `rate_limited`, `tmdb_error`. The CSV is validated *before* the task exists (422 for a bad header, 413 over 25MB, 409 if no TMDB key is configured). RSS items without a `watchedDate` (lists/reviews) are skipped.
- **Storage:** one hidden run per user, `Run(name="Letterboxd Import", game_type="import", status="completed")`, owner participant; imported films are `RunStep(status="watched", watched_at=<diary date, UTC midnight>, logged_by_user_id=user)`. `import` is a reserved `game_type` (`IMPORT_GAME_TYPE` in `models/run.py`): `GET /runs` excludes it, `POST /runs` rejects it, and it has no engine (its `/stats` 400s). Idempotent: an existing `(movie_id, watched date)` is skipped, so re-uploading a file or overlapping with the RSS feed never duplicates, while genuine rewatches on different dates are kept.
- **Memory:** the upload is spooled to `config_dir/imports/<uuid>.csv` in 1MB chunks (the request's `UploadFile` is closed once the 202 is sent) and deleted when the job ends; rows are streamed with `csv.DictReader` and processed in chunks of 25 (concurrent title lookups capped at 5, rewatches share one lookup via a (title, year) memo, steps committed per chunk). Headers are matched case-insensitively (`Name|Title`, `Year`, `Watched Date`, falling back to `Date` for `watched.csv`); `utf-8-sig` is handled.
- **Resolver + rate limits:** `services/tmdb_resolver.py#resolve_movie_id` is the async port of the scraper's multi-pass resolver (exact year -> +-1 -> title only -> slug); the scoring, year order and slug query were extracted from `letterboxd.resolve_tmdb_multipass` into shared helpers (`rank_candidates`, `search_year_order`, `slug_search_query`), so the two cannot drift. It uses the app's `TMDBClient` (global pacing + `Retry-After`) and the **same backoff as the bridge solver**: the loop was extracted into `services/tmdb_backoff.py#fetch_with_backoff` (pause with `asyncio.sleep`, escalate to 30s, give up only at a deadline) and `pathfinder` now calls it. 120s of continuous 429s on one lookup counts as a "stall"; 3 consecutive stalls (or a 401/403 from TMDB) abort the task with `error.code == "import_aborted"`, and everything resolved up to then is already saved, so re-running resumes. Fixed along the way: a `Retry-After: 0` used to be treated as "unset" and slept 2s (`or` bug).
- **Async tasks:** `task_runner.submit_task` now also accepts an `async def` work function (detected with `inspect.iscoroutinefunction`) and runs it on the event loop via `_execute_async` (needed because `TMDBClient` is bound to the main loop's `httpx.AsyncClient`; a worker thread's own loop can't use it). Async jobs must `await ctx.aprogress(...)` (the throttled SQLite write is pushed to a thread) and use `ctx.engine`/`ctx.session()` for DB work; never reuse one `Session` from concurrent coroutines. Queued async tasks poll for a worker slot instead of parking a thread. `TMDBError` now carries `status_code`.
- **Directors:** there was no crew data in the cache, so the Passport join needed new storage: `cached_movie_directors(movie_id, person_id, name)` + `cached_movies.directors_fetched_at` (migration `b8c9d0e1f2a3`; NULL = never fetched, set + no rows = "no director"). Filled by `cache_repo.get_movie_directors` (one `/movie/{id}/credits` call, `job == "Director"`), best effort during import. Films logged in ordinary runs have no directors until looked up, hence `directors_coverage {movies_with_directors, movies_total}` in the Passport payload and the `backfill-directors` task.
- **Passport payload (`GET /passport/me`):** aggregates every `RunStep` with `logged_by_user_id == me AND status == 'watched'` across all runs (import run included). `total_movies_watched` = **distinct films** (a rewatch or a film in two runs counts once); `total_watches` = all log entries; `decades_distribution` `{"1970s": n}` oldest first (per distinct film); `countries` = `[{code, count, merged_from}]` sorted by count; `top_directors` = top 5 `{person_id, name, count}` by distinct films. **Country cleaning:** `movie_origin_country` is a JSON array string (legacy rows may hold a bare code or "US, GB"), so codes are parsed, uppercased, validated as `^[A-Z]{2}$` and de-duplicated; TMDB's historical codes are folded into a successor so they exist on a modern SVG map (`SU->RU, YU->RS, CS->RS, XC->CZ, DD->DE, AN->CW`, recorded in `merged_from`; approximate by design). Co-productions count once per country.
- **Bug fixed:** `letterboxd.ingest_rss_diary` read the TMDB id from `letterboxd:movieId`, but the real feed uses `<tmdb:movieId>` (namespace `https://themoviedb.org`), so RSS entries never carried an id (the test fixture had invented the wrong namespace). Verified against a live feed; RSS imports now skip the title search when the id is present.
- **Dependencies:** added `python-multipart` (required by `UploadFile`). **Not verified live:** the full import against the real TMDB (no API key in this environment); it is covered by respx-mocked tests (CSV/RSS happy paths, idempotence, 429 pause-then-success, persistent-429 abort, cleanup of the spooled file).
- **Files:** `services/{passport_import,passport,tmdb_resolver,tmdb_backoff,task_runner,tmdb,cache_repo,pathfinder,letterboxd}.py`, `api/{routes_passport,routes_runs}.py`, `schemas/passport.py`, `models/{cache,run}.py`, `main.py`, migration `b8c9d0e1f2a3`, tests `test_passport.py`, `test_tmdb_resolver.py`, `test_task_runner.py`, `test_letterboxd.py`.

## Phase 19b: Frontend Passport UI & Map Clearer
- **Passport page (`/passport`, `pages/PassportPage.tsx`)** now reads `GET /api/passport/me` (`usePassport`, key `PASSPORT_KEY`): stat cards (films, total watches, countries, decades), the scratch-off map, a decades bar chart, top-5 directors, Import History, and the old per-run stats (hops/keystone actors) moved into `components/RunStatsSection.tsx` inside a collapsed "Per-run stats" `<details>`.

- **Map Clearer (`WorldMap.tsx`):** a plain inline SVG, no mapping/d3 library. **Map data provenance:** `lib/worldMapData.ts` is *generated* by `scripts/build_world_map.py` from the `@svg-maps/world` package (CC BY 4.0, attribution kept in the file header): the 1.2MB source was converted to absolute coordinates, thinned with Ramer-Douglas-Peucker (tolerance 0.9 on a 1010-wide viewBox), rounded to 1 decimal and stripped of sub-pixel specks and the `um-*` outlying islands -> ~300KB raw / ~100KB gzipped, 250 `<path id="FR">`-style elements with uppercase ISO alpha-2 ids matching the API. It is only loaded through `React.lazy` (own chunk `WorldMap-*.js`), so the rest of the app doesn't pay for it. Regenerate with the commands in the script docstring; don't hand-edit the data file.
- **Shading:** unvisited = `--color-app-surface-hover`, visited = `--color-accent` (so the per-device theme recolors the map) with `fillOpacity = 0.3 + 0.7 * min(1, (count-1)/9)` (1 film faint, 10+ solid); a legend sits under the map. ## Phase 20b: Bridge Solver 2.0 (Path Tagging, Node Swapping, Search Deeper)
- **Path tags:** `services/bridge_paths.py` holds three analyzers run on every built path (primary *and* alternates, so `tags` rides along in the `result` SSE event): `canon_heavy` (2+ path films in `canon_movie_badges`), `multi_country` (3+ distinct origin countries across the path), `epic_runtimes` (2+ films strictly over 150 min). `BridgeNode` gained `runtime` + `origin_countries`; `PathTag` is `{key, label, emoji, detail}` (detail is the chip tooltip). The thresholds are module constants.
- **Gotcha - search/credit stubs have no runtime or country:** films discovered through an actor's filmography are `upsert_movie_stub` rows (no runtime, no `origin_country`), and the solver only fully fetches movies whose *cast* it expands - so tags computed straight off the cache would silently never fire. `hydrate_movies` fetches `get_movie(refresh=True)` for the few path films that are still stubs (before the result is built, with a >=3s floor even if the solve used its whole time limit; best-effort - any failure just leaves that film unhydrated). Don't add it to the per-round hot loop; it only runs on the <=~10 films of a found path.
- **Same-Actor Swap:** `GET /engine/bridge/swap-node` (`movie_id`, `from_movie_id`, `to_movie_id`, `actor_in_id`, `actor_out_id`, optional `exclude_movie_ids`/`run_id`) returns films starring *both* connecting actors plus the two replacement `SharedActorConnection`s (so the actor avatars/characters on the rail stay correct). Actor filmographies are stored as `(movie, actor)` rows in `cached_movie_cast` (credit-sourced rows have `cast_order` NULL), so `Intersection(Actor_X_Movies, Actor_Y_Movies)` is a SQLAlchemy self-join on that table (`.alias()` twice) - pure SQLite once both filmographies are cached (`ensure_filmographies` fetches only missing ones, with a 15s `fetch_with_backoff` deadline; `DeadlineReached` -> 503, `TMDBError` -> 502). Results exclude the replaced film, the rest of the path and (given a `run_id`) the run's history - but never the path endpoints - plus unreleased films (reality filter), sorted by popularity and capped at 12 (`total` reports the uncapped count). Gated by a new `bridge_swap` engine capability. "Broad Route Swap" (A..C re-bridge) is intentionally *not* built yet.
- **Re-tagging a swapped path:** a swap changes runtime/country/canon membership, so the client calls `GET /engine/bridge/tags?movie_ids=...` (hydrates stubs, returns refreshed nodes + tags). The UI clears the old chips immediately and fills them back in when the response lands (and ignores a stale response if the tab/path changed meanwhile).
- **Search Deeper:** `solve_bridge_bipartite(min_hops=N)` (and `?min_hops=` on the stream route, 2..8 via `DEEP_SEARCH_MAX_HOPS`) keeps the same bidirectional BFS but, instead of stopping at the first meeting, scans *every* node both sides have reached (`_collect_deeper_paths`) and only accepts distinct, simple paths of >= N hops (paths that double back through a node are rejected, since with a parent-tree BFS a deeper meeting can reuse a node). `max_depth` is raised to at least `min_hops`. It re-runs inside the same SSE request - shallow levels are cache hits, every new level it reaches is cached - and still honours `bridge_max_duration_seconds` (`timeout` event) and the semaphore; no daemon. The UI appends results as extra tabs ("Deeper - ..."), keeping earlier routes and swaps; the next target is `max(best hops found, last empty target) + 1` so an empty result doesn't loop on the same depth.
- **Frontend:** `BridgePathView` exports `PathTagChips` and shows a shuffle "Swap" button on in-between films; `BridgeSwapPanel` lists alternatives ("Use" replaces the node in state, so Queue Bridge to Active Run uses the edited path); `BridgePage` now keeps `options: BridgeRoute[]` as the source of truth (not `result`), looks up Jellyfin "on server" only for films not seen yet (`lookedUpRef`), and has its own EventSource + cancel for the deeper search.

## Phase 21b: Graph Mutators (Chrono Climb, World Cinema Passport, Auteur Relay)
- **Engines:** `engines/mutators.py` - `MutatorEngine(CineChainEngine)` plus `ChronoClimbEngine`, `WorldPassportEngine`, `AuteurRelayEngine` (game types `chrono_climb`, `world_passport`, `auteur_relay`), registered and so automatically in the Create Run dropdown (they keep `discover_candidates`, so the form treats them as graph modes with the normal ruleset). They drop `bridge_swap` (a same-actor swap can break the mode's rule). Rule violations are **hard blocks** (`ValidationResult.blocked`, 409 even with `force`); a missing cast/director link stays a forceable wildcard miss. Constraint is checked first, link second.
- **Rules:** Chrono: `year(next) > year(prev)` (strict; both years required). Passport: primary (first) `origin_country` differs; **unknown country never blocks** (thinly documented world cinema shouldn't be penalised). Auteur: hops alternate actor/director; the **first hop is free** and whichever kind it uses sets the next requirement (the brief only defined alternation, and a forced opening kind would hide valid openers). A wildcard-forced (no shared link) Auteur hop is recorded as the required kind so the alternation continues.
- **Connection type bookkeeping:** `create_step` now takes server-authoritative metadata from the engine (`link_metadata`): Auteur stamps `transition_metadata.connection_type` (`actor|director`) plus `director_id/director_name` (director hops carry no `actor_id`, so they never count as "keystone actors"), honours a client hint only for the free first hop, and strips a client-claimed `connection_type` on a run's first film so it can't dictate the next hop. `validate_next_step`/`discover_candidates` gained `previous_transition`; `SharedActorConnection`/`DiscoveryConnection` gained `kind` (a director link reuses the actor shape).
- **New data:** `cached_directors` (migration `d0e1f2a3b4c5`) + `get_person_directed_credits` (TMDB `/person/{id}/movie_credits` -> `crew` where `job == "Director"`) + `cache_repo.get_director_credits`: a director's filmography as (movie, director) rows in `cached_movie_directors`. A stub movie gains a *partial* director row (no `directors_fetched_at`), so its full director list is still fetched and replaces it later.
- **Why a second solver (the important design call):** the classic bipartite BFS collapses "which film did I come from" into the actor node, which is wrong as soon as a rule depends on the previous hop. `services/constrained_pathfinder.py` searches at the **movie level**: state = `(movie_id, link kind used to arrive)`, edges are real film-to-film links through one actor *or director*, checked against `PathConstraints` (`services/graph.py`: `movie_ok(earlier, later)`, `endpoint_reason`, `needs_detail`, `alternate_edges`, `use_directors`, `start_tag`). Backward expansion applies the mirrored rule (`movie_ok(predecessor, film)`; the link kind must differ from the one leaving the film); a forward/backward meeting needs compatible tags. `solve_bridge_bipartite(..., constraints=...)` delegates to it (local import - the modules reference each other), so the SSE contract, semaphore, timeout, `min_hops` ("Search Deeper") and the result builder (`_build_result` now emits director links, tags and alternates) are shared. Paths found always satisfy every rule; completeness is best-effort (each round expands at most `pathfinder_actor_credit_limit` frontier films, cache-resident first).
- **World Passport lazy verification:** credit stubs have no country, so the BFS generates neighbours optimistically and verifies the deferred edge when a film is expanded (its detail is fetched then) and, for films discovered on the last hop, by hydrating the candidate path before it is accepted (rejected pairs are remembered). Chrono needs only release years (present on stubs), so it is exact at generation time. Chrono also short-circuits an impossible pair (`exhausted` with `reason: "constraint_impossible"` and a message) instead of searching.
- **Auteur bridge continues the run:** the stream route passes the run's last `connection_type` as `start_connection_type` when the bridge starts from the tail film, so the first bridge hop continues the alternation. Queueing a bridge logs planned steps with `connectionMetadata` (director hops tagged), which the server validates like any step.
- **Candidate pools:** Chrono/Passport filter `discover_candidates` (and suggestions) against the frontier film. Passport hydrates at most `HYDRATE_BUDGET` (30) candidates per request, most popular first; the rest are kept but flagged `constraint_unverified` ("Rule unverified" chip) because dropping them would silently hide valid films - logging re-checks and blocks. Auteur's pool is the actor pool, the director pool (frontier directors' directed filmographies, `kind: "director"` connections), or both, depending on the required kind.
- **Run Detail:** `GET /runs/{id}/constraint` (engine `describe_constraint`) feeds a note on the frontier card ("Next hop must be a Director", "Next film must be released after 1997", "...from a country other than US", "Next hop is free..."); the query lives under the run's key prefix so every step mutation refreshes it. The timeline shows a Director chip for director hops; Bridge page solves under the run's engine only for an explicit `?run_id=` solve, renders director links (clapperboard avatar + "Director"), hides Swap for engines without `bridge_swap`, and shows the impossible-constraint message.

## Phase 21c: The Big Algorithm Sandbox (Aesthetic Gradient + Semantic Trope Web)
- **Engines:** `engines/algorithms.py` - `FeatureEngine(MutatorEngine)` with `AestheticGradientEngine` (`aesthetic_gradient`) and `SemanticTropeEngine` (`semantic_trope`), registered so they appear in the Create Run dropdown automatically. - **Vision (`services/aesthetic.py`):** poster (TMDB `w185`, via new `TMDBClient.get_poster_bytes`, 2 MB cap) is decoded in memory, resized to 50x50, median-cut quantized to 6 colours; the biggest bucket wins. ## Phase 22a: Game Decoupling, Bug Fixes & UI Re-imagining

## Phase 23b: External Embeddings & Alternative Route Breadth
- **Pluggable embeddings (`services/embeddings.py`):** one entry point, `embed_batch(config, texts)`, over `local_onnx` (unchanged), `ollama` (`POST {base}/api/embeddings`, one prompt per call, 4 in flight) and `openai` (`POST {base}/v1/embeddings`; the base URL may or may not already end in `/v1` or `/embeddings`, `openai_url` normalises all three). Config lives in the existing `SystemSetting` overrides (`embedding_provider|base_url|api_key|model`, new `Settings` defaults too); `load_config(session)` reads it per call so a Settings change applies immediately. Vectors are L2-normalised on the way in, whatever the provider returns.
- **Fallback, not failure:** any external error (HTTP status, timeout, bad JSON/shape) becomes `EmbeddingUnavailable`, the whole batch is re-run on local ONNX, and the provider is *suspended for 60 s* (`_suspended_until`). Without the suspension a dead Ollama would cost one 5 s timeout per request. The cap is a real `asyncio.timeout(5)` around the call *plus* a 5 s httpx timeout. Only if local ONNX also can't run does the old lenient "unverified" path kick in. Tests reset the suspension in an autouse conftest fixture - leaking it across tests produced order-dependent failures in the first draft.
- **Vector spaces must not mix (the real design problem):** Ollama's `nomic-embed-text` is 768-d, MiniLM is 384-d, and even equal-width models are different spaces. New `cached_movies.overview_embedding_model` (migration `b4c5d6e7f8a9`; NULL = local MiniLM, so every pre-23b row stays valid) records which model made a vector. `decode_embedding` now accepts any width; `SemanticTropeEngine.measure` returns `None` ("can't tell", never a block) when two films' fingerprints differ; the candidate pool query only loads rows from the frontier's model. `ensure_embeddings` re-embeds films whose fingerprint isn't the configured one - *except* while the provider is suspended, when fallback (local) vectors are accepted rather than re-burning CPU on every request, and upgraded once the provider is back. Changing an overview clears the fingerprint with the vector (`cache_repo`).
- **Settings:** `POST /settings/integrations/test-embeddings` (admin) embeds a dummy sentence with *candidate* settings (blank key = stored key, like the Radarr test) and returns `{ok, latency_ms, dimension, provider, model, detail}`; `check_connection` deliberately skips the fallback so a broken provider reads as broken. The failure text carries the provider's own message (`_error_text`: Ollama `{"error": ...}`, OpenAI `{"error": {"message"}}`) - the dev box has a real Ollama without `nomic-embed-text`, and "model not found, try pulling it first" is far more useful than a bare 404. API keys are masked in `GET /settings/integrations`; saving a non-OpenAI provider clears the stored key and URL/model (empty string = delete override). New `EmbeddingsCard` ("AI & Embeddings") sits under Settings > Integrations (admins only).
- **Disjoint alternative routes:** `/engine/bridge/stream` takes repeated `exclude_movie_ids` (max 200; the two endpoints are always removed from it), unioned with the run's own exclusions. Both solvers already pruned excluded films where they enter the graph, so this was plumbing; the new work is *choosing* routes: `prefer_disjoint_paths` greedily puts routes that share no intermediate film with an earlier pick first (both `pathfinder` and `constrained_pathfinder`; the first-round scan widened from 3 to 12 meeting points so there is something to choose from). Same-middle-film routes through different actors still appear, just after the distinct corridors, so "Alternative Cast Link" labels keep working. Honest limit: at the first round where the two frontiers meet only that depth's meetings exist, so a *different* corridor usually needs the explicit exclusion round below.
- **Bridge UI:** results end with `🔀 Find Alternative Routes` (same max depth, excludes every intermediate of every route already shown, so repeated clicks keep finding new corridors until it says none exist) next to `🔍 Search Deeper (More Hops)`; both share one streaming slot (`ExtraSearchState`) so only one runs. The `🌀 Scenic Detour` badge is derived, not stored (`lib/bridge.isScenicRoute`): a route longer than the shortest one on screen, or the backend's "Underdog / International Pick". If every shorter corridor is blocked the exclusion search naturally returns a longer one - that *is* the scenic detour.
- **Blind Draft:** `🎲 Blind Coin Flip` ignores votes: a light races across the masked cards, decelerates (`70 + step^2 * 1.6` ms) and lands exactly on a pre-picked winner (start index back-computed so the last step is the winner), pauses, then the normal sharp reveal runs. Voting and choosing are disabled mid-flip; timers are cleared on unmount.

Canon Island + an ordering rule stays the "danger" case.

## Phase 24a: Meet in the Middle & Deeper AI Integration
- **LLM service (`services/llm.py`), opt-in and off by default:** providers `off | local_gguf | ollama | openai` (settings `llm_provider|base_url|api_key|model|keep_alive_seconds`, same `SystemSetting` override pattern as embeddings, key masked in `GET /settings/integrations`). `generate(config, system, prompt)` is the one entry point; *every* failure (off, HTTP status, timeout, bad JSON, empty answer, crashed model) is an `LlmUnavailable`, so callers turn it into a message and nothing waits on the model. Remote chat: Ollama `POST /api/chat` (`stream:false`, `think:false`), OpenAI-compatible `POST /v1/chat/completions` (base URL normalised whether or not it ends in `/v1`); output is cleaned (`<think>` blocks, even unbalanced ones, wrapping quotes, whitespace). Qwen gets a `/no_think` soft switch appended to the user turn - without it a 0.8B model spends its token budget reasoning.
- **Memory constraint (local GGUF):** Qwen3.5-0.8B Q4_K_M (`unsloth/Qwen3.5-0.8B-GGUF`, ~530 MB, checked with a HEAD request) runs through `llama-cpp-python`, which is an *optional* extra (`pip install .[llm]`; not a hard dependency because it compiles C++). The model is loaded inside the call (`n_ctx=2048`, `use_mlock=False`, CPU only, <=4 threads), and `_schedule_unload` either unloads straight away (`keep_alive_seconds=0`) or arms a daemon `threading.Timer` that unloads `keep_alive_seconds` (default 300) after the *last* use; each generation re-arms it, the timer takes the same RLock as generation so it can never pull the model out from under a running call, and a crash unloads immediately. `unload_local` closes the model and `malloc_trim`s. Download is a blocking worker-thread step guarded by a lock, like the ONNX one. Tests inject a fake `Llama` and assert load-once/reuse/unload-on-idle/unload-on-crash.
- **Pitch + teaser endpoints:** `POST /engine/pitch {previous_movie_id, candidate_movie_id, link_label?}` -> one punchy sentence (the prompt carries both films' year and plot snippet plus the connecting actor, so the model has something true to say); `POST /engine/teasers {movie_ids<=5}` -> `{id: teaser}` for the Cryptic Blind Draft (system prompt forbids names/twists, and `mask_title` replaces any accidental mention of the title with `▒▒▒`). Partial failures return the teasers that worked; all failing is a 503, off is a 409. Results sit in a 512-entry in-process LRU keyed by provider/model + ids. `GET /engine/llm/status` lets the UI hide the buttons while the model is off (no dead "Why this link?" buttons). `POST /settings/integrations/test-llm` runs one tiny real generation (the local provider unloads right after unless a keep-alive is set).
- **Meet in the Middle engine:** `MeetInTheMiddleEngine` extends `CineChainEngine` (itself a `BaseChallengeEngine`; re-implementing the cast link, pools and stats from the abstract base would have duplicated it) and turns modifiers off - chrono/runtime/cooldown are ordering rules that mean nothing on a chain that grows from both ends. Side is stored in `transition_metadata["tunnel_side"]` (no migration); `split_sides` rebuilds both tracks. `RunCreate.tail_seed_movie_id` (required for this mode, rejected elsewhere, must differ from the head seed) creates the two seed steps; `RunStepCreate/StepValidateRequest.tunnel_side` picks the end - every rule (link, wildcard, no-consecutive-actor, history) now reads the *chosen side's* last step instead of the chronologically last one.
- **Collision Victory:** after the normal link check passes *validly* (a wildcard-forced step can't win), `engine.collides` asks whether the film also connects the opposite frontier (or is that frontier film). If so the step is stamped `collision` + `collision_with` and `evaluate_run_outcome` completes the run with "Chains collided at <Title>!" - the same outcome mechanism the V2 win conditions use. ## Phase 24b: The Blind Fork, Veto Tokens & Tug of War
- **Golden Veto tokens, zero daemons:** `users.veto_tokens` (default 1) + `last_veto_reset_at` (migration `c5d6e7f8a9b0`). The refill is JIT in `get_optional_user` (`services/veto.refresh_veto_tokens`): the first authenticated request more than 30 days after the last reset sets the balance back to 1 and restarts the window. SQLite returns naive datetimes, so the check coerces to UTC first (tested with a naive stamp). Spending is a single atomic `UPDATE ... WHERE veto_tokens > 0` (`consume_veto_token`), so two concurrent requests cannot both spend the last token (tested with two sessions). `/auth/me` now returns the balance.
- **`POST /runs/{id}/veto`:** `target: "fork"` tears up the partner's pending offer, `target: "step"` removes the partner's latest step (never your own, never a seed, only while the run is active). Every precondition is checked *before* the token is spent, so a refused veto costs nothing (tested). The step path reuses the new `_remove_step`, which also reopens a collision/tug victory the way deleting that step always did.
- **Blind Fork:** an opt-in per-run switch (`rules_config["blind_fork"]`, toggled with `PATCH /rules`; refused for Meet in the Middle and engines without a Pick Next pool). Flow: `POST /runs/{id}/fork` (3 distinct films, each pre-validated with the exact `_enforce_run_rules` a real pick gets, needs >= 2 participants) saves `rules_config["pending_fork"] = {offered_by_id, movie_ids, offered_at, links?}`; the partner calls `POST /fork/veto` (free, strikes one film from `movie_ids`, leaving 2 and recording `vetoed_movie_id`) then `POST /fork/accept` (commits one of the two through the shared `_log_step`, then clears the fork). The offerer can neither veto nor accept their own offer (403) and can `DELETE /fork` to withdraw. While an offer is pending *direct logging is refused* (409) - otherwise the offerer could sidestep the partner's veto with a normal pick. Turning the switch off drops a pending offer. The per-film veto is part of the workflow and free; the Golden Veto token is for overruling a whole offer or step. `_log_step` was extracted from `create_step` so the normal and accepted-fork paths cannot drift. The offer carries each card's link metadata (`links`, actor/characters) so an accepted film is logged with the same connection a direct pick would have had.
- **Server-owned rule keys:** `pending_fork`, `tug_scores` and `tug_players` live in a client-writable JSON column, so `create_run` strips them (`blind_fork.strip_server_rules`) - otherwise a client could pre-seed a forged offer or start a Tug run a point from victory (tested). `PATCH /rules` only merges known fields, so it can't write them either.
- **AI Critic Veto Advice:** `/engine/pitch` takes `style: "pitch" | "critic"`; critic uses its own system prompt ("why this hop might be exhausting") and its own cache key, so a plain pitch is never served a critic answer (tested). The overlay's button only shows while the model is on and fetches advice for the remaining films in parallel.
- **Tug of War:** `TugOfWarEngine` extends `CineChainEngine` (so it is a `BaseChallengeEngine` with the shared-cast chain, Pick Next and Bridge Solver) minus the modifiers, which would let one player lock the other out. Rules: `dimension` (`era` = Team A before 1975 / Team B after 2005, in-between films score for nobody; `geography` = Team A US + Europe / Team B rest of world, judged on the *first* production country, unknown country scores nobody) and `target_lead` (default 4, 2..50); `era_a_before`/`era_b_after` can override the cut-offs. Team A is the run owner, Team B the next participant (`tug_players`). Scores are *always recomputed from the watched steps* and cached in `rules_config["tug_scores"] = {team_a, team_b}` for the UI, so deleting a step or marking a planned film watched can never leave them stale; a lead >= `target_lead` completes the run with "Tug of War won by <name>, 3-1!", and deleting the deciding step reopens it. Two small base-engine hooks carry this generically: `prepare_rules_config` (fills defaults on create) and `sync_run_state` (called wherever the run outcome is evaluated, plus on create and step delete).
- **Frontend:** "Tug of War" card (lime) with Era / Geography selectors and a target-lead slider in the New Run modal; `TugOfWarMeter` in the run header draws a rope from -target (Team B, left) to +target (Team A, right) with a knot at the current momentum, initials avatars and live scores at the ends (`role="meter"`). `RunDetailPage` has the "Enable Blind Fork (Offer 3, Veto 1)" switch (the PATCH sends the full rules because `RunRulesUpdate` defaults would otherwise reset the preset/wildcards), an "Offer 3 Films" button that opens Pick Next in a selection mode (cards get "Add to offer", a sticky "Offer to Partner" bar), `ForkOfferPanel` (waiting banner + Withdraw for the offerer; "Partner's Offer" overlay with 🚫 Veto, 🍿 Accept & Watch, AI Critic Veto Advice and a Golden Veto button for the partner) and a `GoldenVetoBar` under a partner's latest step.

## Phase 25b: The Genre Pendulum, Golden Reunions & Character Hopping
- **Genre Pendulum state machine:** `GenrePendulumEngine` extends `MutatorEngine` (a `CineChainEngine`, hence a `BaseChallengeEngine`) as a standalone mode - any film works, shared cast is the usual opt-in hybrid. `rules_config["genre_cycle"]` (default Horror, Thriller, Crime, Comedy) and `["swing_frequency"]` (default 2) give `target = cycle[(steps // frequency) % len(cycle)]`, where `steps` is the number of steps already logged (planned ones count). A film is legal when it (1) shares a genre with the previous film and (2) carries the target; both failures are *blocked* 409s with their own message ("Genre Pendulum: Thriller Crime shares no genre with Horror Two..." / "this swing needs a Horror film (step 2 of 2), but X isn't tagged Horror"), so a wildcard can't skip either (tested). The first film has nothing to overlap but must carry the opening genre (`validate_candidate`, which also rejects a bad seed at creation).
- **How the step count reaches the rule:** the Mutator pipeline's `pair_violation(earlier, later, rules)` has no history, so the pendulum overrides `validate_next_step`, `discover_candidates` and `describe_run_constraint` (all handed the run's history) to stash `len(history)` on the per-request engine instance before delegating. Cycle names are validated and canonicalised against TMDB's fixed movie-genre ids (`TMDB_GENRE_IDS`, so no lookup and aliases like "sci-fi" work); `prepare_rules_config` fills the defaults on create. Each step stores `pendulum_genre`/`pendulum_step`. The Bridge Solver is dropped (no cast graph, and the rule depends on position). A stub whose genres are missing is hydrated before it is judged.
- **Pick Next is filtered server-side:** `discover_rule_candidates` pools cached films carrying the target plus TMDB discover queries for "target + one of the frontier's genres" (`with_genres=27,53` ANDs), then keeps only films that satisfy `pair_violation` - so the pool already matches the swing and the overlap. `/constraint` reports "Current swing: Horror (step 2 of 2)".
- **Golden Reunion & Character Hop (`engines/reunions.py`):** pure functions over credits the engine already fetched. *Golden Reunion*: the earlier film's director also directs the later film AND one of the earlier film's top-5 billed actors is in the later film's cast (the director must *direct* again - a reunion, not a cameo) -> `transition_metadata["golden_reunion"] = {director, actor, director_id, actor_id}`. In `CineChainEngine` directors come from `get_movie_directors` (cached; a failed lookup just means no bonus, it never blocks a step); `CrewCraftEngine` reads them from the credits it already has. *Character Hop*: the same character on both films played by *different* actors -> `["character_hop"] = name`, and where the films share no actor it is itself a valid link (`kind="character"` connection; Auteur Relay opts out - its links must be real actors/directors). Same actor + same character is a normal link with no hop.
- **Character-name matching is heuristic, deliberately conservative:** lowercase, parentheticals and "voice/uncredited" stripped, "Peter Parker / Spider-Man" splits into aliases; generic roles (Self, Extra, Police Officer, Narrator, doctors, guards, ...) and single-word names that are short (< 5 letters) or common first names never match, otherwise half of cinema would link. Only top-N billed cast (`max_cast_order`) is compared. Not covered: Pick Next's pool is built from actor filmographies, so a *pure* hop link (different actors, nothing else shared) isn't offered as a candidate - it is recognised when the film is picked/validated (direct search, `/validate`, logging).
- **Server-owned bonuses:** `golden_reunion` and `character_hop` join `SERVER_OWNED_METADATA` (stripped from client metadata, preserved across `PATCH step`) and are stamped from the engine's `ValidationResult.mechanic` in `_enforce_run_rules` - needed because `create_step` strips server keys from the linked metadata before merging `extra_metadata`. Both survive a step edit; a client can't forge either (tested). A hop logged with no client metadata also records `actor_name`/characters ("A -> B") so the timeline link isn't blank.
- **Frontend:** "The Genre Pendulum" card (red drama-masks icon, a standalone mode, so the cast-link hybrid toggle is offered) with `GenreCycleInput` - a tag input (Enter/comma adds, Backspace removes, suggestions, aliases, TMDB-only validation, reset) and a swing-frequency slider; `PendulumMeter` in the run header ("🎯 Current Swing: Horror (Step 1 of 2) -> Next: Thriller" with the cycle lit and step pips; `lib/pendulum.ts` mirrors the backend formula); `LinkBonusBadges` renders the glowing `🌟 Golden Reunion: Director & Actor` and `🎭 Character Hop: James Bond` on timeline links, step cards, the step detail modal and the direct-search preview. ## Phase 26a: The Daily Bridge ("Cine-Wordle" Puzzle)
- **No cron, one BFS a day:** `services/daily_puzzle.py` derives the day's pair on the first request of a UTC day from `sha256("<date>_<secret key>")` (the effective key, i.e. `SECRET_KEY` or the persisted `secret.key` - `settings.secret_key` alone is `""` by default) and stores it in `daily_puzzles` (migration `f8a9b0c1d2e3`). Later requests - any user, any worker - just read the row, so the pair stays fixed even though the cache grows. A generation lock plus a re-check inside it and an `IntegrityError` fallback keep concurrent first requests to one pair; a failed generation (thin cache) is remembered for 60 s so it isn't re-BFS'd on every poll, and the API answers `503 {code: "puzzle_unavailable"}`.
- **Pair selection:** popular (`popularity > 10`), released films with cached cast; the seeded RNG samples starts, a breadth-first search over the *cached* movie <-> actor/director graph (top-15 billing, reality-eligible films only, ties broken by smallest ids so the same cache gives the same routes) finds targets 3-5 hops away, and the chosen route is **verified hop by hop through the same `find_links` the player is held to** (cached rows are authoritative, but a cast edge learned from an actor's credits may not be top-billed on the film's real cast list). Par = the verified route length.
- **Rules of play:** `validate-hop` accepts any shared top-billed actor *or* shared director. A valid hop is **recorded only if it continues from the chain's tip** of an open attempt (otherwise it's a pure check), so a client can't claim a solve without walking a real chain; reuse of a film is rejected; reaching the target stamps `solved`. `undo` pops the last hop. The optimal route is only revealed once the attempt is solved or forfeited, and so is `convert-to-run` (it would otherwise leak the answer); a solved puzzle can't be forfeited. Convert builds a planned `cinechain` run (the solved chain, or the optimal route after a forfeit) with link metadata in the existing step format, and is idempotent per attempt.
- **Share grid:** one emoji per hop - 🟩 when the film got closer to the target by the cached graph (BFS from the target), 🟨 when it didn't - and the final hop is always 🎯, so the grid has exactly `hops` symbols. (The brief's example shows five symbols for "4 Hops"; I kept the grid and the count consistent.) Grades are computed once, at the solve, and stored on the attempt.
- **Anti-cheat:** `/engine/bridge/stream` *and* the fast `/engine/bridge` return `403 {"code": "anti_cheat_locked", "message": ...}` (a bare JSON body, not `{"detail": ...}`) when the pair - in either direction - is today's stored puzzle and the user has neither solved nor forfeited. The check never *generates* a puzzle: no stored pair means nobody can be playing it. The stream params are `from_movie_id`/`to_movie_id` (the brief's `start_id`/`target_id`). An `EventSource` can't see HTTP statuses, so `/tools/bridge` re-asks the failed URL once (`lib/antiCheat.ts`, aborted immediately on a 200) to tell a lock from a lost connection, then shows the "🔒 Playing today's Daily Puzzle?" banner.

## Phase 26b: The Rabbit Hole (Rogue-like Survival Mode)
- **Engine:** `engines/rabbit_hole.py` - `RabbitHoleEngine(CineChainEngine)` (so still a `BaseChallengeEngine`; it keeps the cast/director link, discovery and bridge solver) plus a pure tier state machine: `tier_for_depth(len(steps))` -> Freefall (0-4), The Retro Lock (5-9, year < 2000), Tower of Babel (10-14, `original_language != "en"`), The Micro-Clock (15-19, runtime < 100) and The B-Movie Abyss (20+, rating < 6.0). The depth is the number of steps already in the run, i.e. the *6th* film is the first one under Tier 2. It reaches the rule through `validate_next_step` / `discover_candidates` / `describe_run_constraint` (they get the history) and is stashed on the per-request engine instance, like the Genre Pendulum.
- **Soft rules, paid in lives:** a tier breach or a missing link is `valid=False, blocked=False`, so it is only loggable with `force`. `_enforce_run_rules` now asks the engine class (`uses_lives`) what a forced step costs: a Rabbit Hole run spends one of `rules_config["lives_remaining"]` (never a wildcard; stamps `life_lost` on the step; a double violation still costs one life) and with no lives left the forced hop is refused (`409 "No lives remaining"`). `prepare_rules_config` always starts a run on full lives (`max_lives` 1-9, default 3), so a client can't hand itself extra lives, and `PATCH /rules` can't touch them. Zero lives is *not* the end by itself - only a legal film continues - the run ends when the player gives up: `PATCH status=forfeited` goes through a new `BaseChallengeEngine.forfeit_outcome` hook, and at zero lives the Rabbit Hole turns it into `failed` with `"Succumbed to the Rabbit Hole at Depth {n} ({tier name})"`. I deliberately did *not* auto-fail on a dead end server-side: an empty candidate list can also be a transient TMDB hiccup, and a GET shouldn't be able to kill a run. The Pick Next drawer instead shows an "Accept your fate" button when lives are 0 and the pool is empty.
- **Unknown data never costs a life:** `compliance()` is tri-state (True / False / None). Stubs lack runtime and rating, so the pool is hydrated within the usual budget and films that still can't be judged stay in, flagged `constraint_unverified` (`tier_compliant: null`); the hop check treats unknown as legal. The discover endpoint returns a bare list, so besides the per-candidate field the same warning plus the whole HUD state (`RabbitHoleState`: depth, tier, rule, lives, next tier, hops until it) is also on the run's `/constraint` response. The warning appears 1-2 hops before a boundary ("begins on the next hop" / "in 2 hops").

## Phase 27b: The Bounty Board & The Rotten Tomatoes Split
- **Bounty Board (`services/bounties.py`):** a meta-mechanic, not an engine: `rules_config["bounty_board"] = True` (validated as a real boolean; `BaseChallengeEngine.supports_bounty_board` is False for March Madness, which logs steps outside `_log_step`, and the Rabbit Hole, which has lives not wildcards -> 422) makes `create_run` call `prepare_board`: `wildcards_budget = 0`, `active_bounties` = 3 distinct random ids, `completed_bounties = []`. Catalogue: `short_king` (runtime < 90), `time_capsule` (< 1960), `hidden_gem`, `foreign_horizon` (language != en and no US among the origin countries), `female_gaze` (any director with TMDB gender 1), `epic_odyssey` (> 150). The cache has no vote count, so `hidden_gem` uses the spec's fallback, TMDB popularity < 12.
- **Award flow:** `_log_step` evaluates the movie *before* inserting the step (the evaluation can need TMDB fetches - full detail for runtime/language/countries, the crew for director genders, re-read when cached before genders were stored - and those commit). A TMDB failure just means no award. At most one bounty completes per step (board order); it's stamped `transition_metadata["completed_bounty"]` (+ `bounty_replacement`), then `award` does `wildcards_budget += 1`, moves the bounty into `completed_bounties` and appends the replacement, drawn from never-completed bounties not on the board (once all six are done, any off-board bounty can return). Deleting the step runs `revoke` (budget back down, clamped at 0; bounty back on the board, its replacement off), so undo can't farm wildcards. `PATCH /rules` ignores `wildcards_budget` on a bounty run. `active_bounties`/`completed_bounties` are server-owned rules and `completed_bounty`/`bounty_replacement` server-owned step metadata, so neither can be forged.
- **Rotten Tomatoes Split (`engines/rt_split.py`, game_type `rt_split`):** a `TrackerEngine`. OMDb has no RT *audience* score, so the audience side is the IMDb rating x10; the Tomatometer is `rotten_tomatoes` ("88%"). Both come from `cached_movie_ratings`; a film qualifies at `abs(critic - audience) >= 25` (exactly 25 counts), anything else (or no scores) is a hard block. Team Critic 🍅 = the owner, Team Audience 🍿 = the next partner (same ordering as Tug of War). `RunStepCreate.household_score` (1-100, validated by pydantic) is required on a watched step; the server settles it into `critic_score/audience_score/divergence/household_score/point_to` (all server-owned metadata): strictly closer to the critics = Team Critic, **otherwise (ties too) Team Audience**, as specified. Scores are recomputed from the steps into `split_scores`/`split_players` (`sync_run_state`); first to `target_points` (default 3, 1-20) completes the run with `"Split Decided: Team Critic 🍅 (Alice) wins 3-2!"`, and deleting the deciding step reopens it. Planned steps are rejected for split runs (a point needs a rating). The rating is warmed through OMDb in the route (`create_step` gained the OMDb dependency) because engines only hold the session and TMDB client.
- **Pool:** `GET /runs/{id}/split-pool?scan=N` returns cached films with a 25+ gap, biggest first, minus those already logged; `scan` (<= 20) first fetches OMDb ratings for the N most popular cached films that have none yet (OMDb has no bulk endpoint, so the pool grows gradually). Without an OMDb key the pool stays empty and the UI says so.

On the run page `BountyBoardPanel` (collapsible; three bounty cards with icon, criterion, `+1 🎟️ Wildcard`, wildcard balance; a pop-in "Bounty Complete" banner with a bouncing reward chip and a slide-in replacement card, triggered only by steps that appear *after* the page loaded, `prefers-reduced-motion` respected) and `SplitBoard` (head-to-head scoreboard, settled-films list, pool cards with `SplitMeter` - `🍅 Critics: 88% | 🍿 Audience: 52% (Δ 36%)` - and a "Log Movie" `HouseholdRatingModal` that previews who wins the point as you type). Criteria text in `lib/bounties.ts` mirrors the backend catalogue by hand.

## Phase 27d: AI Living-Room Polish (Bracket Commentary & Dynamic Bounties)
- **Tale of the Tape:** `llm.generate_matchup_commentary(movie_a, movie_b, config=None)` takes two bracket film cards (`bracket_films` entries) and returns one boxing-announcer sentence. Like `extract_tropes`, `config` defaults to the `.env` settings and the route passes the admin's saved `load_config(session)`; model off returns `""`, model on but failing raises `LlmUnavailable` (never cached). `POST /runs/{id}/bracket/commentary {matchup_id}` returns `{commentary, enabled, cached}`: 404 for an unknown matchup, 409 until both films are in it, 503 on a model failure, an empty answer (nothing stored) when the model is off, and otherwise the line stored in `rules_config["bracket_commentary"][matchup_id]` - generated once, first writer wins if two partners click at once, and it survives `_decide`'s deep copy. `bracket_commentary` is a server-owned rule.
- **AI bounties:** the model never decides whether a film qualifies. It writes `{title, icon, description, rule}` where `rule` is 1-3 conditions that must all hold, each `runtime{min,max}`, `year{min,max}`, `decade` (normalised to a year range), `genre` (a TMDB genre name -> id map) or `keyword` (words searched in title + tagline + plot, prefix match). `normalize_rule`/`parse_custom_bounty` validate everything (ranges, genre whitelist, 3-40 char title, duplicate titles on the board or already generated), tolerate code fences and `<think>` blocks, and get one retry; `custom_bounty` turns a stored definition into a normal `Bounty` whose `check` runs the rule against `MovieFacts` (which gained `genre_ids` and `text`). Missing data never satisfies a condition. Definitions live in `rules_config["custom_bounties"]` (server-owned) and the board references `ai_xxxxxx` ids; `resolve`/`active_bounties` accept either kind and silently drop an id whose definition is gone or broken.
- **When one is generated:** (1) automatically, inside `evaluate`, when completing a bounty leaves no *static* bounty that is neither on the board nor completed (the literal "all 6 done" can't happen while the board always holds three, so this is the real exhaustion point) - `BountyAward(completed, replacement, custom)` carries the new definition and `award` stores it; if the model is off or fails, the old recycling of static bounties applies. (2) on demand, `POST /runs/{id}/bounties/custom` ("✨ Roll Custom Bounty"): the oldest board slot is swapped for an AI bounty (the displaced one returns to the pool uncompleted, no wildcard change); 409 with no board / model off / an AI bounty already on the board, 503 if the model can't produce a valid one. ## Phase 28a: The Perfect Marathon Router (Traveling Cinephile Problem)
- **Whiplash cost (`services/marathon_router.py`, pure Python, no I/O):** a hop between two films costs `0.40*genre + 0.25*year + 0.15*runtime + 0.20*rating`, with genre = `1 - Jaccard(genres)`, year = `min(|dy|/50, 1)`, runtime = `min(|dm|/60, 1)`, rating = `min(|dr|/5, 1)` (IMDb when cached, else TMDB's `vote_average`). A field either film lacks costs a neutral `0.5`, so missing data neither flatters nor punishes a film. Weight overrides are rescaled to sum to 1, so scores stay comparable (and the defaults are unchanged); negative or all-zero weights are a 422.
- **Optimizer:** a marathon is an *open* path, and the cost is symmetric. N <= 8: every permutation is scored (reverses skipped). N > 8: simulated annealing over 2-opt reversals (`T0=100, alpha=0.995, 10,000` iterations) with an O(1) boundary-edge delta per move, then a 2-opt + relocate descent polish. Lesson: `T0=100` against costs in 0..1 means the schedule is effectively greedy after ~1,500 iterations, so a single chain finished 1-3% off the Held-Karp optimum; keeping the best of 4 seeded chains (`RESTARTS`) brought that to ~0.1-0.7% for ~80ms at 25 films (<90ms measured, ~25KB peak, so inside the 250ms / 15MB budget). Seeded from the film ids, so the same input always yields the same order; it never returns anything worse than the input order (then improvement is `0%`).
- **Labels:** cost < 0.30 `Smooth Transition`, < 0.55 `Gentle Shift`, else `Tonal Whiplash`. Each transition also carries a `summary` (`1980s Science Fiction Harmony` when smooth, otherwise the weighted-largest gap: `Drama ──► Comedy`, `1950s ──► 2020s`, `95 min ──► 180 min`, `Rated 4.1 ──► 8.2`) plus the four raw deltas.
- **API (`api/routes_router.py`):** `POST /api/tools/router/optimize` (4-25 distinct ids; films missing from the cache - or cached without a runtime - are fetched first, TMDB 404 -> 404, other TMDB failures -> 502) returns the order, initial/optimized score, improvement %, transitions, the films in order (poster, genres, runtime, rating), `method`, applied weights and `calculation_ms`. `POST /api/tools/router/convert-to-run` (`run_name`, 2-25 distinct ids) creates an active **Roulette** run (any film is legal, so no cast-link rule can reject the marathon) with the sequence as `planned` steps in exactly the order given (`logged_at` offset by 1ms each, as in the Daily Bridge conversion); steps after the first carry `transition_metadata["marathon_router"] = {whiplash, label}` (default weights).
- **Frontend (`/tools/router`, `pages/MarathonRouterPage.tsx`, `lib/marathonRouter.ts`):** a "Perfect Marathon Router" card (compass icon) in the Tools hub. Selector = My Watchlist (reads `/tools/bingo/watchlist`, cache only) or Search Films, up to 20 picks shown as numbered chips, plus "🎲 Pick 10 Random from Watchlist". Three sliders (Genre Harmony 40, Decade Proximity 25, Pacing / Runtime 15) map to the weights; Rating / Mood keeps its default 0.20 share. The calculate button holds a >= 900ms compass animation so a ~10ms answer still reads as work. Result: the `✨ Tonal Whiplash Reduced by 58%! (Initial Score: 8.4 ──► Optimized: 3.5)` banner, a vertical timeline of cards with a colour-coded chip between each pair, and "🍿 Queue as Challenge Run" (editable name) which converts and opens the run. Changing the selection clears a stale result.

## Phase 28b: The Historical Time-Travel Engine (Setting Era vs. Release Year)
- **Schema:** `cached_movies.narrative_year` (signed int, negative = BCE) and `narrative_era_label` (migration `b1c2d3e4f5a6`, batch add/drop; upgrade -> downgrade -> upgrade verified). NULL = not resolved yet. Re-fetching a film's detail (`upsert_movie`) only clears a *"Contemporary"* era when the release date changed; a real era or a manual edit is never touched.
- **Resolution (`services/historical_era.py`):** `resolve_narrative_era(movie, overview, keywords) -> (year, label)` is the pure core: (1) TMDB keywords, slugified and aliased (`World War II`/`WWII` -> `world-war-ii`) against the spec's taxonomy (`TAXONOMY`, ordered so concrete eras beat the generic futures: a `dystopia` + `world-war-ii` film is 1943); (2) the overview - `Nth century` (also `BC`), `N BC`, `N AD`, else the first 4-digit year; (3) otherwise `(release year, "Contemporary")`. The LLM one-shot (`{"year": int, "era": str}`, reply parsed strictly) sits between 2 and 3 inside the async `ensure_narrative_era` / `ensure_narrative_eras`, which also fetch the keywords (new `TMDBClient.get_movie_keywords`; `find_keyword_ids` for the pool) and save the result. Lesson: **only save an answer you trust.** Keywords unreachable, a stub with no plot yet (the real detail is fetched first), the model on-but-failed, or the model on-but-skipped (pool films, `allow_llm=False`, so one Pick Next can't fire dozens of generations) all return the contemporary default *unsaved*; saving it would pin a guess as fact and stop the real answer from ever being tried. With the model off, "Contemporary" is a legitimate answer and is saved.
- **Engine (`engines/historical_time_travel.py`):** `HistoricalTimeTravelEngine(MutatorEngine)` (a `BaseChallengeEngine` via `CineChainEngine`), game type `historical_time_travel`, `rules_config["direction"]` = `"climb"` (default, forward) or `"descent"`, validated. A hop must move *strictly* in that direction by setting year (the same year is blocked); violations are hard blocks no wildcard can buy back; shared cast is the usual opt-in hybrid. `mechanic` -> `transition_metadata`: `narrative_delta`, `narrative_year`, `narrative_era_label`, `direction`. Candidates carry `narrative_year`, `narrative_era_label`, `narrative_delta`, nearest leap first; films that could not be dated are kept but flagged `constraint_unverified` (logging re-checks). Returns `{tmdb_id, narrative_year, narrative_era_label, source: resolved|manual|default}`. Run steps now carry `movie_narrative_year` / `movie_narrative_era_label` read live from the cache (`_step_movie_info`, which also replaced `_step_colors`), so the first film and manual edits show without touching step metadata.

## UX & Game-Systems Audit (static + live-flow, pre-implementation)
- **Shared-Device Attribution:** `RunStep.logged_by_user_id` identifies the **authenticated account** that logged the step. Passport history (`services/passport.py` L67, L127) relies on that meaning, so it must **not** dictate in-game team assignment. In the living-room case one logged-in account logs both players' picks. Game-side attribution (e.g. Tug of War's `tug_team`) must be an explicit, server-validated, server-owned field on `transition_metadata`. The same applies to seeds: they are stamped `watched` under the creator and leak into Passport and Tug scoring unless flagged (`seed`). Golden Veto "partner's step" checks have the same blind spot.
- **Zero-Sum Engine Deadlocks:** symmetric scoring engines (Tug of War: +1 for your territory, the opponent symmetric) need **strict turn-order enforcement** *and* anti-stalemate mechanics. Rational alternating play otherwise oscillates `0 → +1 → 0` forever, and without turn order one player can win alone (reproduced live: "won by Ana, 4-0" after 3 solo picks plus a pre-scored seed). Required pieces: turn validation (409 on an out-of-turn pull), a dominant-strategy breaker (Invasion Steal), momentum (streaks) and a provable termination bound (Sudden Death shrinking the target). Prove termination in tests with a property test, not just example games.
- **TMDB Unrated Fallbacks:** TMDB returns `vote_average = 0.0` for **unrated** films, so any rating-based validation (Rabbit Hole Tier 5 "rated under 6.0", B-movie filters) must also verify `vote_count` (e.g. ignore `vote_average` when `vote_count < 10` → treat as unknown/unverified). Without OMDb configured the IMDb fallback disappears and `vote_average` is the only signal, which makes this mandatory, not optional.
- **Also learned in the live audit (see `docs/MASTER_UX_AUDIT.md` Phase 5):** `cache_repo.get_movie()` can return search/credit **stubs** with no `origin_country`, and steps copy those fields permanently, so hydrate before denormalising. `upsert_cast` needs a SAVEPOINT for `CachedMovieCast` rows (cold-cache race → 500). The shared `Modal` has no focus trap, scroll lock or stack-aware Esc, so fix it once in the primitive. Pick Next renders roughly 900–1,300 cards without pagination. Absolute-positioned dropdowns inside `overflow-y-auto` modal bodies get clipped, so use a portal popover.
- **Dev-environment gotcha:** `frontend/node_modules/.vite/deps` may be **root-owned** (left behind by the Docker dev stack), so `npm run dev` fails with `EACCES … unlink`. Don't `chown`/`sudo` the user's tree. Run Vite with a temporary `cacheDir` through a wrapper config instead. For live testing, point `CONFIG_DIR` at a scratch directory so the real `config/cinechain.db` is never touched.

## Phase S6: Tug of War v3 & strategic legibility

## v4 Mechanics, Taxonomy & Core UX Audit (post-v3.0.0 playtest, pre-implementation)

- **Inheritance is not configuration:** Tug of War requires shared cast only because it subclasses `CineChainEngine`. Link rules exist in five shapes (`CineChainEngine.validate_primary`, `MutatorEngine.optional_cast_link`/`require_cast_link`, Auteur Relay alternation, Crew & Craft, `graph.find_links`/`PathConstraints`). New modes should declare a traversal policy (`LinkPolicy`, blueprint F9) and derive capabilities from it, not from the class tree.
- **A plane needs a neutral band:** Tug's `geography` dimension returns neutral only for unknown countries, so "Bank" is reachable only through missing data. Any two-pole mechanic must measure pole balance and neutral share on the household cache before offering it.
- **Stamp evidence that a fold depends on:** `RunStep` stores only title, poster, year and country. A rule over any other fact (genre, language, setting year) must stamp server-owned evidence at log time, or a later cache refresh silently rescores finished games.
- **Compute verdicts last:** Rabbit Hole wrote `constraint_unverified` before `filter_by_modifiers` and `pool_options.shape_pool` hydrated more films, so a card could show a cached runtime and "Rule unverified" together. Annotate candidates once, after every hydration pass, and send the rule in an evaluable form so the client can resolve it as facts arrive.
- **One vocabulary for film properties:** at least nine independent predicate vocabularies exist (S8 predicates, AI bounty rules, client-side Bingo, Roulette SQL, Chaser, seed requirements, conditions, title overlays, region/genre maps), with different thresholds for the same named concept ("short" is <85, <90, ≤85, <100 or ≤95). `feasibility.Evidence` loads the whole cache into Python per request. The Facet Engine (F5) replaces these with typed, indexed, versioned rows and a compiled query AST.
- **Inverse directions come from data, not features:** `ascending_numbers` has no count-down and the predicate registry had `year_lt`/`rating_lt`/`popularity_lt` without their inverses, so every random draw pushed towards older, worse or obscurer films. Declare ordered facets once and derive both directions.
- **A queued state needs a way out:** Career/Auteur/Expedition boards rendered "Queued" as a terminal label because step actions live in the step-bound `MovieDetailModal` opened only from `ChainTimeline`, which those modes replace. RT Split rejected planned steps outright because settlement needed the household score at log time. Move settlement to the watch transition and give every surface the same queue/log actions.
- **Partial success is success:** `canon_hydrate` failed the whole task when one film lacked a country/date; list persistence deleted and committed before re-inserting; unmatched entries vanished; `tmdb_type == "tv"` was parsed but ignored. Record per-item outcomes and keep the last good snapshot in one transaction.
- **Respect source signals before scraping:** `https://tvtropes.org/robots.txt` (checked during the audit) is Cloudflare-managed and declares `Content-Signal: search=yes, ai-train=no`, with `ai-input` unspecified. The hybrid design ingests only trope link lists, validates against our own definitions with existing local models, is opt-in and attributed, and stops on any challenge.
- **Vault concepts are not code:** "the heaviness PID controller" exists only in `docs/planning/Future Game Modes & Engines Vault.md`; its shipped precursor is the Chaser (`pool_options.needs_chaser`/`is_chaser`), whose Drama-or-135-minute trigger is culturally biased. Say so explicitly when a request names an unbuilt system.
